# Codex引き継ぎ計画：リブレ2 → GAS → BigQuery（14日間）

## 1. 次のCodexへの依頼

この文書を引き継ぎ仕様として、日本語で実装を進めてください。まず作業ディレクトリと既存コード・AGENTS.mdを確認し、取得APIの現在の仕様を一次資料・OSSのコードで再確認してください。最初の実装目標は、GASでLibreLinkUpから1回取得し、値と日時を確認できることです。その後、BigQuery保存、15分間隔の定期実行、14日後の自動停止を実装してください。

通常の実装判断はこの計画を基に進めてください。認証情報やユーザー側の画面操作が必要な場合は、その時点で必要なものだけを案内してください。実行していないAPI疎通や未確認の測定仕様を「検証済み」と扱わないでください。

今回の依頼は引き継ぎ文書の作成までです。この文書によってGASやクラウドの設定変更・稼働開始が済んだわけではありません。

## 2. 目的と決定事項

- 日本版FreeStyleリブレ2とiPhoneを使用する個人用の収集システム。
- グルコース値をGoogle BigQueryへ蓄積し、後で分析できるようにする。
- 実行環境はGoogle Apps Script（GAS）。Cloud Run・GitHub Actions・自作iOSアプリは今回の実装対象から外す。
- 正常な初回収集から14日間を収集期間とする。開始日はこの文書の作成日に固定しない。
- 15分間隔で取得可能な履歴を重ねて取得し、分析時に重複を除く。
- パスワード・トークン等はスクリプトプロパティに保持し、トークンを再利用する。
- 終了日時以降に起動した処理で、この収集処理のトリガーを削除して停止する。
- 最終成功時刻とエラーを記録する。

15分はAPIへのアクセス間隔であり、センサーの測定間隔ではない。履歴取得により短い実行遅延を補える設計にするが、欠測ゼロを保証しない。

## 4. 全体構成

| 要素 | 役割 |
| --- | --- |
| iPhoneの公式LibreLink | リブレ2から読み取り、Abbottクラウドへ送信 |
| LibreLinkUpの閲覧用アカウント | 自分の測定データの共有を受ける |
| GASの時間主導トリガー | 約15分ごとに収集関数を実行 |
| GASのAPIクライアント | ログイン、共有対象選択、最新値・履歴の取得 |
| GASのBigQueryサービス | 測定レコードを保存 |
| BigQueryの分析用ビュー | 再取得による重複を除いた測定値を提供 |

LibreLinkUpはクラウド経由の非公式API連携。日本版・現行アカウントでの動作を最初に検証する。GASはNode.js実行環境ではないため、Axios等の既存依存をそのまま使わず、UrlFetchApp等に置き換える。

## 5. APIの調査メモ（再確認が必要）

以下は会話で参照したOSSに基づく。Abbottの公開・保証された開発者仕様ではない。

| 処理 | パス・情報 |
| --- | --- |
| ログイン | POST /llu/auth/login、JSON bodyにemail/password |
| 地域指定 | ログインレスポンスのdata.redirect/data.region |
| 認証トークン | data.authTicket.token、有効期限も確認する |
| 閲覧者ID | data.user.id |
| 共有対象一覧 | GET /llu/connections |
| 測定対象ID | 一覧のpatientId。閲覧者IDとは別 |
| グラフ・最新値 | GET /llu/connections/{patientId}/graph |
| 最新値の場所 | data.connection.glucoseMeasurement |
| 履歴の場所 | data.graphData |

確認したクライアントのヘッダーはproduct: llu.android、version: 4.16.0、Content-Type: application/json。認証後はAuthorization: Bearer <token>、Account-Id: <閲覧者user.idのSHA-256、小文字16進数>を付加する。バージョンを現在の正解と断定せず、設定値として変更可能にする。

最初の接続先の候補はhttps://api.libreview.io。地域変更が返った場合は、確認済みのAbbottホストの許可リストに限定して切り替える。任意の返却URLへ認証情報を転送しない。

規約・プライバシー通知への同意、メール確認が要求された場合は停止し、公式アプリで本人が完了する手順を案内する。HTTPステータスとJSON内statusの両方を検査する。

graphはクライアント文書上では概ね直近12時間分。logbookには別のイベント履歴があるが、14日間の連続測定データを一括取得できる根拠にはしない。今回の収集は稼働開始後に蓄積する方式とする。

## 6. 設定と状態管理

スプレッドシートは必須にせず、単独GASプロジェクトで動作させる。スクリプトのタイムゾーンはAsia/Tokyoとし、API日時の解釈は別途検証する。

| プロパティ案 | 内容 |
| --- | --- |
| LLU_EMAIL / LLU_PASSWORD | 閲覧用アカウントの認証情報 |
| LLU_API_BASE / LLU_VERSION | 検証済み接続先と通信バージョン |
| LLU_PATIENT_ID | 本人が確認した対象者ID |
| LLU_TOKEN / LLU_TOKEN_EXPIRES_AT / LLU_ACCOUNT_ID_HASH | 再利用する認証状態 |
| BQ_PROJECT_ID / BQ_DATASET / BQ_TABLE / BQ_LOCATION | 保存先 |
| RUN_ID / START_AT / END_AT | 収集期間と実行キャンペーンの識別子 |
| RUN_STATUS | 未開始・稼働中・停止・最終同期失敗等 |
| LAST_SUCCESS_AT / LAST_MEASUREMENT_AT | 書き込み成功時刻と最新測定時刻 |
| CONSECUTIVE_FAILURES / LAST_ERROR_CODE | 秘密情報を含めない失敗状態 |
| NEXT_RETRY_AT | レート制限等による待機期限 |

プロパティに大量の測定履歴は保存しない。プロジェクトの編集者はプロパティを読める前提で、自分だけが編集する。パスワード、トークン、ログインレスポンス全体をログやソースへ出力しない。

GASのBigQuery高度なサービスを有効化し、トリガー作成者に必要なBigQuery権限を付ける。GCPプロジェクト側のAPI有効化も確認する。サービスアカウントJSON鍵は不要な構成を優先する。

## 7. 保存と重複排除の方針

初期案は「追記用テーブル＋重複排除ビュー」。小規模・14日限定のため、毎回のMERGEや外部ステージングを必須にしない。書き込みAPI・課金・GASからの利用可否を確認し、より簡単な方式があれば理由を残して採用してよい。

| カラム案 | 型 | 用途 |
| --- | --- | --- |
| run_id | STRING | 今回の14日収集の識別子 |
| patient_id | STRING | 測定対象者 |
| measured_at | TIMESTAMP | 検証済みルールでUTCへ変換した測定時刻 |
| glucose_mg_dl | FLOAT64 | ValueInMgPerDl |
| trend_arrow | INT64・NULL可 | 存在する場合のみ保持 |
| record_source | STRING | latestまたはhistory |
| fetched_at | TIMESTAMP | API取得日時 |
| raw_measurement | JSON | 認証情報を含まない元の測定オブジェクト |
| observation_key | STRING | 安定した測定識別キー |

観測キーは実データ確認後に決定する。API固有の測定IDがなければ、対象者＋正規化測定時刻を基礎にする。センサー切り替え・同時刻の別レコードがあり得る場合は追加識別子を含める。値そのものをキーに含めて訂正値を別測定扱いしない。

分析用ビューでは、同一観測キーの最新取得レコードを採用する。latestとhistoryが同じ測定を指すか、同時刻で値が違う場合の優先順位、trendのNULL処理を実データで決める。insertIdを使用する場合も、それだけで完全な重複排除ができると仮定しない。

BigQueryの部分失敗を確認し、全行の保存完了後にのみLAST_SUCCESS_ATを更新する。期間内の測定を失敗なく保存した場合、取得件数がゼロでも最新測定時刻は別に追跡し、データ停止を見逃さない。

TimestampとFactoryTimestampにはタイムゾーン指定がない例がある。Date.parseに任せず、公式アプリの表示時刻と照合して明示的に変換する。解釈不能な日時を現在時刻で補完しない。必要なら元JSONを隔離保存し、正常な測定として扱わない。

## 8. 14日間の開始・終了・再実行

- setupは設定検証・テーブル等の準備に限定し、繰り返してもトリガーを増殖させない。
- 手動の1回取得とBigQuery書き込みが成功してからstartCollectionを実行する。
- 初回正常同期の基準時刻をSTART_AT、START_AT＋14×24時間をEND_ATとし、再実行で期間を延長しない。
- 初回に取得した開始前履歴は、保存対象外とするかrawとして明確に区別する。分析対象はSTART_AT以上END_AT未満。
- LockService等で手動実行とトリガーの同時実行を避ける。
- 期限前は重ねて履歴取得。最新値だけの取得にしない。
- 期限到達後の最初の起動で、期間内の末尾を回収する最終同期を1回試み、その成否にかかわらず当該収集トリガーを削除する。
- 最終同期失敗は状態に残す。自動停止後の再取得は明示的な手動操作とし、自動で稼働期間を延長しない。
- GASのトリガーは正確な時刻の実行を保証しない。停止は期限後の次回起動時であり、厳密に期限の瞬間ではない。
- stopCollectionを用意し、いつでも当該収集を止められるようにする。他用途のトリガーやBigQueryデータは削除しない。

終端直前のデータ反映遅延や長時間障害により欠測が残る可能性は、最終品質レポートに明示する。

## 9. エラー処理・運用確認

- トークンは可能な範囲で期限まで再利用し、毎回ログインしない。
- 認証失敗時の再ログインは制限する。403をすべて期限切れと扱わない。
- 429・lockedでは連続ログインを止め、Retry-After等を参照して次回以降へ延期する。
- 長いUtilities.sleepを使わず、NEXT_RETRY_ATで待機を表現する。
- 5xxや通信失敗は次回の重複取得で回復できるようにする。
- ログは実行結果、件数、日時、匿名化したエラー分類に絞る。
- checkStatusで終了予定、最終成功、最新測定、失敗回数を確認できるようにする。
- 失敗はGAS実行履歴にも残す。メール等への独自通知は現時点の必須要件ではなく、追加するなら宛先と送信意図を確認する。

## 10. 実装順序と成果物

1. **作業環境・API仕様確認**：既存リポジトリと設定を確認。GAS向けHTTP・SHA-256の実装方法、BigQueryサービスを確認。
2. **1回取得**：共有対象の選択、ログイン、履歴取得まで実装。複数対象を勝手に先頭から選ばない。ユーザーが認証設定し、表示値と時刻を検証できる手順を提供。
3. **データ整形**：日時・単位・NULL・最新値と履歴の扱いを確定。最古・最新日時、間隔、件数を確認。
4. **BigQuery保存**：DDLと分析用ビュー、書き込み処理、部分失敗処理を用意。同じ取得データを2回保存してもビューで重複しないことを確認。
5. **状態・トリガー**：開始、定期実行、トークン保持、ロック、期限、停止、状態確認を追加。
6. **実機で開始**：設定値・権限を確認して稼働開始。START_AT/END_ATをユーザーに明示。
7. **終了確認手順**：トリガー停止、日別件数・欠測、認証情報の片付け方法を文書化。データは残す。

成果物はGASソース（.gs）、appsscript.json、BigQuery DDL・ビューSQL、セットアップ/開始/停止/障害対応をまとめたREADME、秘密情報を含まない設定一覧。ファイルの分割数は小さく保ち、Docker・Cloud Run・GitHub Actionsのデプロイ構成は作らない。

## 11. 完了条件・確認方法

- [ ] 日本版アカウントで取得し、公式アプリと値・時刻を照合できる。
- [ ] BigQueryに正常な測定時刻とmg/dLの値が保存される。
- [ ] 同一レスポンスを再処理しても分析用ビューの測定数が増えない。
- [ ] NULL、日時変換、認証エラー、429、部分書き込み失敗を扱える。
- [ ] 定期トリガーが1つだけ存在し、15分間隔に設定される。
- [ ] 再起動やsetupの再実行でEND_ATが延長されない。
- [ ] テスト用の短い期限/注入した時刻で、最終同期・停止を検証できる。
- [ ] 他のトリガーや保存データを削除しない。
- [ ] 秘密情報がログ・ソース・検証結果に含まれない。
- [ ] 実行した検証と未実行の検証が明確に報告される。

テストは日時変換・重複排除・停止境界・部分失敗等に絞る。実アカウント未設定の段階ではモックによる検証と手動検証手順を完成させ、疎通成功と偽らない。
